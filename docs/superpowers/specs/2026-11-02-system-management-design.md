# เมนู "จัดการระบบ" สำหรับผู้ดูแลระบบและหัวหน้างาน (พี่เดชา)

วันที่: 2026-11-02 · สถานะ: รอผู้ใช้รีวิว · เส้นทาง: architectural

## 1. เป้าหมาย

ผู้ดูแลระบบ (ADMIN) และหัวหน้างานที่เป็นผู้อนุมัติ (MANAGER, ตอนนี้คือพี่เดชา) ต้องดูแลข้อมูลหลักของระบบ
ได้เอง โดยสร้าง ดู แก้ไข และลบได้ครบจากเมนูเดียว ไม่ต้องแก้ฐานข้อมูลตรง

สิ่งที่ผู้ใช้สั่งไว้: "เพิ่มเมนู ฝั่งผู้ดูแลระบบ และพี่เดชา ให้สามารถ CRUD ได้ทุกอย่าง" และอนุมัติดีไซน์ในแชตแล้ว
ว่าใช้ค่าตามที่เสนอทั้ง 5 ข้อ (ขอบเขต เมนู ความหมายของการลบ สิทธิ์พี่เดชา ความปลอดภัย)

เกณฑ์ว่าสำเร็จ:
- ADMIN และ MANAGER เห็นเมนู "จัดการระบบ" และทำ CRUD ผู้ใช้ คำขอ บทความ KB ได้ตามกฎด้านล่าง
- EMPLOYEE และ IT_STAFF เปิดหน้าหรือเรียก server action ของเมนูนี้ไม่ได้ (ตรวจฝั่งเซิร์ฟเวอร์ทุกจุด)
- MANAGER ยกระดับตัวเองเป็น ADMIN ไม่ได้ และแตะบัญชี ADMIN ไม่ได้
- คำขอที่ถูกลบหายจากทุกรายการ แดชบอร์ด และตัวนับ SLA แต่กู้คืนได้ พร้อมประวัติว่าใครลบเมื่อไหร่
- UI 3 ภาษา (ไทย/ลาว/อังกฤษ) และใช้งานได้บนมือถือ ไอแพด และจอกว้าง ตามที่ทำไว้แล้วทั้งระบบ

## 2. ขอบเขต

อยู่ในขอบเขต: ผู้ใช้, คำขอ, บทความฐานความรู้ (KB)

อยู่นอกขอบเขตรอบนี้:
- ประเภทคำขอ หมวดหมู่ และ SLA (อยู่ในโค้ด ถ้าจะ CRUD ต้องย้ายลง DB เป็นงานแยก)
- ลบคำขอถาวร (purge), แก้ `type` และ `details` ของคำขอ, การทำงานเป็นชุด (bulk), นำเข้า CSV
- สิทธิ์ละเอียดกว่า ADMIN/MANAGER (ยังคง 1 ผู้ใช้ = 1 role)
- การแจ้งเตือน

## 3. สถานะปัจจุบัน (ที่ดีไซน์นี้ต่อยอด)

- `src/app/actions/users.ts`: `updateUser` แก้ได้แค่ role กับ isActive และต้องเป็น ADMIN; ไม่มีสร้างหรือลบ
- ผู้ใช้เกิดตอนล็อกอิน Google ครั้งแรก (`src/lib/users.ts` upsert ตามอีเมล) ถ้าสร้างแถวไว้ก่อน
  ระบบจะผูก `googleSub` ให้ตอนเข้าครั้งแรก จึงลงทะเบียนล่วงหน้าได้โดยไม่ต้องแก้ flow ล็อกอิน
- `src/app/actions/kb.ts`: `saveArticle` สร้าง/แก้ได้เฉพาะ staff (IT_STAFF, ADMIN); ไม่มีลบ
- คำขอ: ไม่มีแก้ไขและไม่มีลบ; การเปลี่ยนสถานะ ยกเลิก อนุมัติ เปลี่ยนผู้อนุมัติมีอยู่แล้วและคงเดิม
- FK `ServiceRequest.requester`, `RequestComment.author`, `RequestEvent.actor`, `KbArticle.author` เป็น
  `onDelete: Restrict` จึงลบผู้ใช้ที่มีประวัติไม่ได้

## 4. ดีไซน์

### 4.1 โครงสร้างเมนู

เมนูเดียวในแถบข้าง: **"จัดการระบบ"** (ไอคอน settings) ไปที่ `/admin` แทนรายการ "จัดการผู้ใช้" เดิม
เห็นเฉพาะ ADMIN และ MANAGER ภายในหน้ามีแท็บ:

| แท็บ | เส้นทาง | เนื้อหา |
|---|---|---|
| ผู้ใช้ | `/admin/users` | รายการ ค้นหา/กรอง เพิ่ม แก้ ลบ |
| คำขอ | `/admin/requests` | รายการทุกสถานะ (รวมที่ถูกลบ), สร้างแทนผู้อื่น, แก้, ลบ/กู้คืน |
| ฐานความรู้ | `/admin/kb` | รายการทุกบทความ (รวมที่ซ่อน), เพิ่ม แก้ ลบ |
| บันทึกการเปลี่ยนแปลง | `/admin/audit` | รายการอ่านอย่างเดียว ใครทำอะไรกับผู้ใช้/KB เมื่อไหร่ |

`/admin` เด้งไป `/admin/users` แท็บเป็นแถบเลื่อนแนวนอนบนจอแคบ ตารางใช้รูปแบบ การ์ด/ตาราง ตาม breakpoint
เดียวกับหน้ารายการคำขอ (การ์ดต่ำกว่า `lg`) `admin/layout.tsx` กันหน้าด้วย `requireSystemManager`
แต่ layout อย่างเดียวไม่ใช่การควบคุมความปลอดภัย ทุก server action ตรวจสิทธิ์เองอีกชั้น

### 4.2 กฎสิทธิ์ (`src/lib/permissions.ts`, pure module + เทสต์)

- `canManageSystem(viewer)`: role เป็น ADMIN หรือ MANAGER
- `requireSystemManager()` ใน `dal.ts` (redirect `/` ถ้าไม่ผ่าน) ใช้กับทุกหน้าและ action ของเมนูนี้
- `canModifyUser(actor, target, change)` คืน `{ ok } | { ok: false, reason }`:
  1. actor ต้อง `canManageSystem`
  2. actor แก้ role, isActive ของตัวเอง หรือลบตัวเองไม่ได้ (แก้ชื่อ แผนก เบอร์ของตัวเองได้)
  3. actor ที่เป็น MANAGER แตะบัญชี ADMIN ไม่ได้เลย (แก้ ปิด ลบ) และตั้งใครเป็น ADMIN ไม่ได้
  4. ADMIN ทำได้ทุกอย่างตามข้อ 1–2 (รวมตั้ง/ถอด ADMIN คนอื่น)
  - ผลที่ตามมา: ADMIN คนสุดท้ายลบหรือลดสิทธิ์ไม่ได้ เพราะมีแต่ ADMIN อื่นที่แตะได้ และตัวเองแตะตัวเองไม่ได้
- `canEditKb(viewer)`: staff หรือ `canManageSystem` (เพื่อให้ MANAGER สร้าง/แก้บทความจากเมนูนี้ได้)
- `canDeleteKb(viewer)`: `canManageSystem` เท่านั้น (IT_STAFF ล้วนยังเพิ่ม/แก้ได้เหมือนเดิม แต่ลบไม่ได้)
- `canEditRequest(viewer, request)`: `canManageSystem` และคำขอยังไม่ถูกลบ
- ADMIN_EMAILS ยังทำงานเดิม: อีเมลในรายการจะถูกตั้งเป็น ADMIN ทุกครั้งที่ล็อกอิน ถ้าจะลดสิทธิ์ต้องเอา
  อีเมลออกจาก `.env` ก่อน (หน้าแก้ผู้ใช้แสดงข้อความเตือนนี้เมื่อเป้าหมายอยู่ใน ADMIN_EMAILS)

### 4.3 ผู้ใช้

- **สร้าง (ลงทะเบียนล่วงหน้า)**: อีเมล (ตัวพิมพ์เล็ก, ซ้ำไม่ได้, ต้องผ่าน `ALLOWED_EMAIL_DOMAINS` ถ้าตั้งไว้),
  ชื่อ, role, แผนก, เบอร์ ไม่มี `googleSub` จนกว่าเจ้าตัวล็อกอิน; role ADMIN ตั้งได้เฉพาะ ADMIN
- **แก้**: ชื่อ แผนก เบอร์ role และเปิด/ปิดใช้งาน ตามกฎ `canModifyUser`
- **ชื่อ**: ตอนนี้ล็อกอิน Google เขียนทับ `name` ทุกครั้ง ซึ่งจะทำให้การแก้ชื่อไม่มีผล จึงเปลี่ยนเป็น
  ใช้ชื่อจาก Google เฉพาะการล็อกอินครั้งแรก (ตอน `googleSub` ยังว่าง) หลังจากนั้นผู้ดูแลเป็นเจ้าของชื่อ;
  `image` ยังอัปเดตจาก Google เหมือนเดิม
- **ลบ**: ลบถาวรได้เฉพาะผู้ใช้ที่ไม่มีการอ้างถึงเลย คือไม่เป็น requester, ผู้ comment, ผู้ทำเหตุการณ์ (actor),
  ผู้เขียน KB, assignee, approver, decidedBy หรือ deletedBy ของคำขอใด ถ้ามี ระบบปฏิเสธพร้อมข้อความ
  "ผู้ใช้นี้มีประวัติการใช้งาน ให้ปิดการใช้งานแทน" และแสดงจำนวนที่อ้างถึง กฎนี้เป็นฟังก์ชัน pure
  `userDeletionBlockers(counts)` เพื่อเทสต์ได้ และตัวนับมาจาก `_count` ของ Prisma
  (นับรวม assignee/approver/decidedBy ด้วยเจตนา เพราะ `SetNull` จะทำให้คำขอค้างไม่มีผู้รับผิดชอบ)

### 4.4 คำขอ

- **สร้างแทนผู้อื่น**: ใช้ฟอร์มสร้างคำขอเดิม เพิ่มช่อง "ผู้ขอ" (เลือกผู้ใช้ที่ active) ที่แสดงเฉพาะ
  system manager กฎการอนุมัติใช้กับผู้ขอที่เลือก (`requiresManagerApproval(ผู้ขอ, ...)`) ผู้อนุมัติห้ามเป็นผู้ขอ
  เหตุการณ์ `CREATED` บันทึก actor เป็นผู้ที่สร้างจริง และมีบันทึกว่าสร้างแทน
- **แก้**: หัวข้อ รายละเอียด ลำดับความสำคัญ วันที่ต้องการ `requestedForName` และผู้อนุมัติ
  (ใช้กฎเปลี่ยนผู้อนุมัติเดิม: ต้องเป็น MANAGER ที่ active และไม่ใช่ผู้ขอ)
  ไม่แก้ `type`, `details`, สถานะ, SLA ผ่านหน้านี้ (สถานะ/SLA/ผู้รับผิดชอบยังเปลี่ยนที่หน้ารายละเอียดคำขอ
  ตาม workflow เดิม) ถ้าประเภทหรือรายละเอียดเฉพาะประเภทผิด ให้ลบแล้วสร้างใหม่
  เหตุการณ์ใหม่ `EDITED` เก็บชื่อฟิลด์ที่เปลี่ยนใน `toValue` (เช่น `title,priority`)
- **ลบ (soft)**: ปุ่มลบมีกล่องยืนยัน ตั้ง `deletedAt` และ `deletedById` เขียนเหตุการณ์ `DELETED`
  คำขอที่ลบแล้ว: ไม่ขึ้นในรายการ แดชบอร์ด "งานของฉัน" "รออนุมัติ" ตัวนับป้าย (badge) และสถิติ SLA;
  เปิดลิงก์ตรงแล้วเป็น 404 สำหรับทุกคน ยกเว้นผู้ดูแลในแท็บคำขอของเมนูนี้ที่เห็นพร้อมป้าย "ถูกลบ"
  และปุ่ม **กู้คืน** (เหตุการณ์ `RESTORED`) เลขที่คำขอไม่ถูกนำกลับมาใช้
- การลบ/แก้/กู้คืนใช้ได้กับคำขอสถานะใดก็ได้ รวมที่ปิดแล้ว

### 4.5 ฐานความรู้

- `/admin/kb` ใช้หน้า `/kb/new` และ `/kb/[id]/edit` เดิมสำหรับเพิ่ม/แก้ (ขยายสิทธิ์เป็น `canEditKb`)
- เพิ่ม action `deleteArticle` ลบถาวรได้ (ไม่มีตารางอื่นอ้างถึง) พร้อมกล่องยืนยัน ต้องผ่าน `canDeleteKb`
- สลับเปิด/ซ่อน (`isPublished`) ได้จากรายการโดยไม่ต้องเข้าหน้าแก้

### 4.6 บันทึกการเปลี่ยนแปลง (audit)

เหตุการณ์ของคำขอใช้ `RequestEvent` ที่มีอยู่ ส่วนผู้ใช้และ KB ไม่มีที่เก็บ จึงเพิ่มตารางเล็ก
`AuditLog` (`id`, `actorId` → User Restrict, `action`, `entity` เช่น `USER`/`KB_ARTICLE`, `entityId`,
`summary` ข้อความสั้น เช่น อีเมล/ชื่อบทความ และฟิลด์ที่เปลี่ยน, `createdAt`) เขียนเมื่อ สร้าง/แก้/ลบ
ผู้ใช้และบทความ KB สรุปข้อความเก็บเป็น snapshot ตอนนั้น เพราะเป้าหมายอาจถูกลบไปแล้ว
แท็บ `/admin/audit` แสดงรายการล่าสุดแบบแบ่งหน้า 14 รายการ อ่านอย่างเดียว

## 5. ข้อมูลและ migration

migration ใหม่ `20261104000000_system_management`:
- `tbl_service_requests`: เพิ่ม `deleted_at timestamp null`, `deleted_by_id text null` (FK → `tbl_users`,
  `onDelete: Restrict`) และ index `(deleted_at)`
- enum `EventAction`: เพิ่ม `EDITED`, `DELETED`, `RESTORED`
- ตารางใหม่ `tbl_audit_logs` ตามข้อ 4.6 พร้อม index `(created_at)` และ `(entity, entity_id)`

ทุกคำสั่งใน `src/lib/queries.ts` ที่อ่าน `serviceRequest` ต้องใส่ `deletedAt: null` (รายการ รายละเอียด
แดชบอร์ด `listMyTasks` `countMyTasks` `listPendingApprovals` `countPendingApprovals` ตัวนับ SLA และการนับในหน้า
ภาพรวม) ขั้นตอนทำงานรวมการไล่ค้น `serviceRequest.` ทั้งโปรเจกต์เพื่อไม่ให้ตกหล่น และ action เดิมที่รับ
`requestId` (comment, เปลี่ยนสถานะ, ยกเลิก, อนุมัติ ฯลฯ) ต้องปฏิเสธคำขอที่ถูกลบ
`listRequests` มีตัวกรอง `deleted: "only" | "include"` ใช้เฉพาะในเมนูจัดการระบบ

## 7. การทดสอบ

- เทสต์ pure ด้วย vitest: เมทริกซ์ `canManageSystem`/`canModifyUser` (ทุก role × เป้าหมาย × ตัวเอง/คนอื่น),
  กรณี ADMIN คนสุดท้าย, `userDeletionBlockers`, `canEditKb`/`canDeleteKb`/`canEditRequest`
- เทสต์ i18n guard เดิมครอบข้อความใหม่ทั้งหมด (3 ภาษา)
- ตรวจกับ DB ชั่วคราว (ขั้นตอนเดิม: scratch Postgres พอร์ต 54329) ก่อนใช้ migration กับ DB จริง:
  ลงทะเบียนล่วงหน้าแล้วล็อกอินผูก `googleSub`, ลบผู้ใช้ที่มี/ไม่มีประวัติ, ลบแล้วกู้คืนคำขอ,
  คำขอที่ลบไม่โผล่ในรายการ/แดชบอร์ด/ป้ายตัวเลข, MANAGER แตะ ADMIN ไม่ได้
- ตรวจหน้าจริงในเบราว์เซอร์ที่ 375px, 768px และจอกว้าง ทั้งสามภาษา; รัน `tsc`, `eslint`, `vitest`

## 8. ความเสี่ยง

- ลืมใส่ `deletedAt: null` ในบางคำสั่ง → คำขอที่ลบยังโผล่ ลดความเสี่ยงด้วยการไล่ค้นทุกจุดและตรวจหน้าจริง
- การเปลี่ยนวิธีตั้งชื่อตอนล็อกอินกระทบผู้ใช้เดิม: ชื่อใน Google ที่เปลี่ยนภายหลังจะไม่ตามเข้ามาอัตโนมัติ
  (ผู้ดูแลแก้ในเมนูได้)
- MANAGER มีอำนาจกว้างขึ้นมาก (ลบคำขอ ลบผู้ใช้ที่ไม่มีประวัติ) จึงต้องมีกล่องยืนยันและบันทึกการเปลี่ยนแปลงตามข้อ 4.6

เสนอให้ตรวจเป็นพิเศษตอนรีวิว ตัดออกได้โดยไม่กระทบส่วนอื่น:
1. แท็บและตาราง `AuditLog` (ข้อ 4.6)
2. เปลี่ยนให้ใช้ชื่อจาก Google เฉพาะการล็อกอินครั้งแรก (ข้อ 4.3)
3. ห้ามลบผู้ใช้ที่ถูกอ้างถึงโดย assignee/approver/decidedBy แม้ FK เป็น `SetNull` (ข้อ 4.3)
4. หน้าแก้คำขอไม่แตะ `type`/`details`/สถานะ (ข้อ 4.4)
5. MANAGER แตะบัญชี ADMIN ไม่ได้แม้แต่แก้โปรไฟล์ (ข้อ 4.2)
